# US-13 — Registro de usuario

Historia: https://github.com/msancheza1/MailWatch_P2/issues/40

## Alcance y criterios

| Criterio | Resultado |
| --- | --- |
| CA-US13-01 / CP-US13-01 | Una solicitud válida crea una cuenta y responde 201. |
| CA-US13-02 / CP-US13-02 | Un correo existente se rechaza con 409; la cuenta y su contraseña se conservan. |

En la pantalla de acceso, **¿No tienes cuenta? Crear cuenta** abre el formulario
con correo, contraseña y confirmación. Las contraseñas deben coincidir. Al
completarlo se muestra una confirmación y se vuelve al login, con el correo
normalizado ya diligenciado. El usuario inicia sesión con su contraseña.

La cuenta se guarda en la tabla `users` existente, con el mismo formato de hash
`scrypt` y sal aleatoria utilizado por US-14. El registro no devuelve la
contraseña ni su hash, ni crea una sesión automáticamente. El login, la
restauración de sesiones y el cierre de sesión continúan disponibles.

## Validaciones

- Correo obligatorio, de hasta 254 caracteres, con formato básico de correo.
- Se eliminan espacios alrededor del correo y se convierte a minúsculas.
- Contraseña obligatoria de 8 a 1024 caracteres; se rechaza si solo contiene espacios.
- Los espacios significativos y las mayúsculas de la contraseña se conservan.
- Confirmación de contraseña en el formulario, antes de enviar la solicitud.
- Se rechazan correos existentes aunque cambien sus mayúsculas. También se
  reconocen cuentas antiguas almacenadas con mayúsculas.
- El índice UNIQUE existente sobre `users.email` y `ON CONFLICT` resuelven dos
  registros simultáneos del mismo correo normalizado: una cuenta y un rechazo.
- Los campos ID, rol, hash y token enviados por un cliente no se utilizan.

Solo login y registro son públicos. Las demás rutas conservan la protección
por sesión existente. No se incluyen recuperación de contraseña, verificación
por correo ni cambios de roles en esta historia.

## API

`POST /auth/register`, sin token:

```json
{
  "email": "persona@ejemplo.com",
  "password": "MiClave123!"
}
```

Respuesta 201:

```json
{
  "user": {
    "id": 1,
    "email": "persona@ejemplo.com"
  }
}
```

Errores: 400 para datos inválidos, 409 para un correo ya registrado, 500 para
un fallo de almacenamiento. El formulario diferencia el duplicado de un
problema de conexión y mantiene la posibilidad de reintentar.

## Aplicar el cambio en una rama nueva

Base: `111100ffa9e19dfcb34f33efbc44af2210ff6ecc` de `main`.
Este parche contiene únicamente US-13; no incluye ni elimina el trabajo de US-08.

Con una copia de trabajo limpia y `US-13.patch` en la raíz:

```powershell
git fetch origin
git switch -c feature/us-13-registro origin/main
git apply --check US-13.patch
git apply US-13.patch
cd backend
npm ci
npm run test:registration
```

Para usar la aplicación, iniciar backend y frontend como de costumbre:

```powershell
# Terminal del backend
npm run start:dev
```

```powershell
# Otra terminal, desde la raíz
cd frontend
npm ci
npm run dev
```

El uso de la aplicación necesita el PostgreSQL configurado para el login.
No se agrega una migración nueva: se reutiliza `003_auth.sql`. Si es una base
vacía, primero ejecutar las migraciones existentes con `npm run db:migrate`.
La prueba automática no requiere PostgreSQL externo ni Docker.

Si US-08 todavía está en otra rama, no aplicar este parche encima de esa rama:
crear esta rama desde `origin/main` y abrir un PR independiente. Si ambos PR
modifican los scripts de `package.json`, al fusionar conservar tanto
`test:feedback` como `test:registration` y la dependencia de PGlite una sola vez.

## Pruebas

Requisito: Node.js 24 y npm. Desde `backend`:

```powershell
npm ci
npm run test:registration
```

Compila NestJS y ejecuta 13 pruebas de integración con rutas, autenticación,
hashes y SQL reales sobre PostgreSQL embebido (PGlite). Solo se sustituye el
transporte de base de datos; no se toca la base del usuario ni se valida el
pool de red contra PostgreSQL externo.

Incluye los dos casos exigidos y verifica login posterior, sesión, logout,
normalización, duplicados concurrentes, sal aleatoria, límites, entradas
inválidas, rutas protegidas y errores de almacenamiento.

GitHub Actions ejecuta el comando mediante `.github/workflows/registration.yml`.

Prueba manual:

1. Abrir la aplicación y seleccionar **Crear cuenta**.
2. Completar un correo nuevo y dos contraseñas iguales de al menos 8 caracteres.
3. Confirmar el mensaje de éxito y entrar con las nuevas credenciales.
4. Cerrar sesión y volver a registrar el mismo correo: debe rechazarse.
5. Probar el correo en mayúsculas: también debe rechazarse.
6. Probar dos contraseñas distintas: debe aparecer el aviso sin crear cuenta.

La validación automatizada no sustituye una sesión manual de navegador ni una
prueba en el PostgreSQL de despliegue.
