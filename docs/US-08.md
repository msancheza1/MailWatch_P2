# US-08 — Reportar falsos positivos y negativos

Historia: https://github.com/msancheza1/MailWatch_P2/issues/10

## Comportamiento

Después de analizar un correo, el usuario puede **Marcar como seguro** o
**Marcar como peligroso**, tanto en correos disponibles como en cuarentena.
La última valoración y su fecha aparecen junto al correo y se recuperan al
recargar la página o volver a iniciar sesión con la misma cuenta.

La valoración del usuario se guarda separada de la clasificación automática:
no se sobrescriben los análisis, no se libera la cuarentena ni se cambian las
reglas automáticamente. Esta historia reúne retroalimentación para evaluar y
mejorar la precisión; no incorpora reentrenamiento automático.

Se guarda en `email_feedback`: correo, usuario autenticado, análisis evaluado,
riesgo original, valoración, tipo de reporte y fecha. El servidor determina
el usuario a partir de la sesión; no acepta una identidad enviada por el cliente.
Las modificaciones conservan el historial. Reintentar la misma valoración para
el mismo análisis no duplica registros.

| Riesgo automático | Valoración | Reporte |
| --- | --- | --- |
| HIGH / Malicious | Seguro | Falso positivo |
| LOW / Safe | Peligroso | Falso negativo |
| MEDIUM / Suspicious | Seguro | Falso positivo |
| MEDIUM / Suspicious | Peligroso | Falso negativo |
| LOW / Safe | Seguro | Confirmación |
| HIGH / Malicious | Peligroso | Confirmación |

`Suspicious` se trata como una advertencia que el usuario puede corregir en
cualquiera de las dos direcciones. Las confirmaciones no se cuentan como errores.

## Instalación en una copia existente

Base de este cambio: `111100ffa9e19dfcb34f33efbc44af2210ff6ecc` de `main`.
No incluye los cambios propuestos anteriormente para CP-US05-01.

Con el archivo `US-08.patch` en la raíz y una copia de trabajo limpia:

```bash
git fetch origin
git switch -c feature/us-08-feedback origin/main
git apply --check US-08.patch
git apply US-08.patch
cd backend
npm ci
```

Configurar la conexión a PostgreSQL como en el resto de la aplicación. El
`docker-compose.yml` del proyecto expone el puerto **5433**:

```powershell
# PowerShell, en la terminal del backend
$env:PGPORT = "5433"
```

```bash
# Bash, en la terminal del backend
export PGPORT=5433
```

Con PostgreSQL iniciado, aplicar la nueva migración y arrancar:

```bash
npm run db:migrate
npm run start:dev
```

En otra terminal, desde la raíz:

```bash
cd frontend
npm ci
npm run dev
```

Iniciar sesión con una cuenta existente. Si se necesita una cuenta, el script
existente `npm run user:create -- correo@ejemplo.com` requiere configurar
`MAILWATCH_PASSWORD` (8–1024 caracteres) en el entorno del backend.

La migración `004_feedback.sql` es aditiva e idempotente. No borra tablas ni
registros existentes. En una base ya creada, reiniciar Docker por sí solo no
aplica nuevas migraciones: ejecutar `npm run db:migrate`.

## API

Todos los endpoints requieren `Authorization: Bearer <token>`.

- `POST /feedback/:id`, cuerpo `{ "category": "Safe" }` o
  `{ "category": "Malicious" }`: devuelve el registro guardado (201).
- `GET /feedback`: devuelve la última valoración del usuario autenticado para
  cada correo. El historial completo se conserva en la tabla.
- `GET /emails` conserva su contrato y añade `risk_level`, para que los botones
  y la clasificación sigan disponibles después de recargar la página.

Errores: 400 para identificadores/valoraciones inválidos; 401 sin sesión;
404 si el correo no existe; 409 si todavía no se ha analizado. Los botones
se deshabilitan hasta analizar el correo y mientras se guarda una operación.

## Pruebas

Desde `backend`, con Node.js 24:

```bash
npm ci
npm run test:feedback
```

Ejecuta 10 pruebas de integración con la aplicación NestJS compilada, la
autenticación real y las migraciones del proyecto sobre PostgreSQL embebido
(PGlite). Solo se sustituye el transporte de base de datos. No requiere Docker,
no accede a la base del usuario ni valida el pool de red de `pg`.

Cubre falsos positivos/negativos, confirmaciones, persistencia, historial,
reintentos, análisis posteriores, aislamiento por usuario, autenticación,
validación y fallos de almacenamiento. GitHub Actions ejecuta este comando
mediante `.github/workflows/feedback.yml`.

Comprobación manual:

1. Iniciar sesión y cargar el dataset.
2. Analizar un correo malicioso y marcarlo como seguro en cuarentena.
3. Analizar un correo seguro y marcarlo como peligroso en disponibles.
4. Recargar: confirmar que las dos valoraciones continúan visibles.
5. Cambiar una valoración y comprobar que la última elección se muestra.
6. Entrar con otra cuenta: sus valoraciones son independientes.
7. Comprobar que carga del dataset, análisis, alertas, sensibilidad y cuarentena
   continúan accesibles.
